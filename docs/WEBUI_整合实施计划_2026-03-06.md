## 1. 文档目的

本文将“WebUI 取代桌面 GUI”的方向文档，细化为一份可执行的实施计划。

这份计划只回答四个问题：

1. 先做什么
2. 后做什么
3. 每个模块的目标是什么
4. 什么叫阶段完成

本文不替代详细 issue/工单拆分，但应足够支持后续排期。

---

## 2. 实施总原则

## 2.1 以 `ProWorkspace` 为唯一整合骨架

后续 WebUI 不再双线发展。

统一原则：

1. `web_ui/src/views/pro_workspace/` 作为主工作站骨架。
2. 通用页面中已成熟的真实能力，只做吸收，不再平行增强。
3. 重复能力只保留一个正式入口。

## 2.2 先闭环，后打磨

开发顺序必须遵守：

1. 先打通业务闭环。
2. 再做信息架构收口。
3. 最后做视觉统一与体验打磨。

不能反过来先花大量时间做视觉整理，因为当前主要问题不是样式，而是主流程未收口。

## 2.3 先领域收敛，再页面收敛

统一顺序：

1. 先统一 API 层
2. 再统一 store 层
3. 再统一页面入口
4. 最后删除重复页面

---

## 3. 阶段划分

建议分为六个阶段：

1. `P0` 主线冻结与边界确认
2. `P1` API / Store 架构收敛
3. `P2` Voices + Assets 闭环
4. `P3` Workspace 生产闭环
5. `P4` System + Settings + Export 收口
6. `P5` App Shell 与重复页面退役

---

## 4. P0：主线冻结与边界确认

目标：

1. 明确 WebUI 是唯一未来前端。
2. 明确 `ProWorkspace` 是唯一整合骨架。
3. 明确桌面 GUI 不再接新功能。
4. 明确通用 Web 工作台中哪些模块保留、哪些被吸收。

### 4.1 任务

#### P0-A 产品边界确认

输出：

1. 确认最终一级页面结构：
   - Workspace
   - Voices
   - Assets
   - Library
   - Export
   - System

验收：

1. 团队内部对最终信息架构无歧义。

#### P0-B Web 主线确认

结论要求：

1. `ProWorkspace` 为正式主线。
2. `VoiceManager` / `ScriptEditor` / `ExportPanel` 等通用页中成熟功能允许继续使用，但必须纳入主线整合计划。

验收：

1. 所有后续新功能需求都能归属到主线模块。

#### P0-C 桌面 GUI 冻结约束

冻结规则：

1. `ui/` 不再新增功能。
2. 只允许：
   - 严重 bug 修复
   - 数据兼容修复
   - Web 迁移所需的兼容修复

验收：

1. 新需求默认先看 Web，不再默认往桌面加。

### 4.2 P0 交付物

1. 本文档
2. `桌面 GUI 退场检查清单`

## 5. P1：API / Store 架构收敛

目标：

1. 解决当前 `cosyvoice.ts` 与 `pro_client.ts` 双客户端并存的问题。
2. 解决 `pro_* store` 与 `voices/project/tts/...` 双状态模型并存的问题。
3. 为后续模块迁移提供稳定底座。

### 5.1 模块目标

#### A. API 层

目标：

1. 建立统一请求底座：
   - URL 规范化
   - Header / API Key 注入
   - 错误处理
   - Blob / auth audio 支持
2. 在统一底座上按领域拆分：
   - `voiceApi`
   - `assetApi`
   - `batchApi`
   - `synthesisApi`
   - `systemApi`

不再保留：

1. `pro_*` 与 `cosyvoice` 风格分裂的长期状态。

#### B. Store 层

目标状态域：

1. `workspace`
2. `voices`
3. `assets`
4. `library`
5. `system`
6. `export`
7. `app`

说明：

1. `tts` 可并入 `system` 或 `app` 的连接配置。
2. `pro_voice` 与 `voices` 最终只能保留一套。
3. `pro_task` 与 `project` 中任务逻辑最终只能保留一套。

### 5.2 具体任务

#### P1-A API 收敛任务

1. 列出现有 Web 端所有 API 能力及其调用者。
2. 标注重复与缺失。
3. 设计统一 client 分层。
4. 明确所有音频播放都走统一 auth-aware 方案。

验收：

1. 新页面不再直接依赖两套 client。
2. 任何一条 API 能力都有唯一入口。

#### P1-B Store 收敛任务

1. 明确每条业务数据的权威 store。
2. 列出可删除的重复状态。
3. 制定迁移顺序，避免一次性大重构。

验收：

1. voice 数据只由一套 store 管理。
2. task/workspace 数据只由一套 store 管理。

### 5.3 P1 依赖

无前置业务依赖，但建议在任何大功能开发前完成。

### 5.4 P1 完成标准

1. API 分层方案确定。
2. Store 分层方案确定。
3. 迁移主线已经有统一数据源与统一请求层。

## 6. P2：Voices + Assets 闭环

这是第一优先级最高的业务阶段。

目标：

1. 让桌面 `voice_settings.py` 的核心业务闭环可以在 WebUI 上完成。
2. 让 WebUI 不再依赖桌面端去做 voice/asset 管理。

### 6.1 模块定义

#### Voices 模块必须覆盖

1. voice 列表
2. 新建 voice
3. 编辑 voice
4. 删除 voice
5. 角色/情绪分组
6. prompt/ref 配置
7. compile
8. 批量改名
9. legacy 导入入口

#### Assets 模块必须覆盖

1. 资产列表
2. 资产上传
3. 资产删除
4. 资产试听
5. 绑定 / 解绑
6. note / transcript 编辑
7. linked / unused 过滤
8. 清理未使用资产

### 6.2 任务拆分

#### P2-A Voice CRUD 正式化

目标：

1. 迁移主线中的 voice 创建、编辑、删除都使用真实 API。
2. 清理本地假实现：
   - `addVoiceLocal`
   - 本地删除但不落库

验收：

1. 在正式主线上完成的 CRUD 操作，刷新后仍存在。
2. 任何 voice 操作不再依赖临时内存状态。

#### P2-B 情绪管理正式化

目标：

1. 将 `ProEmotionEditor` 从“情绪标签本地编辑器”升级为真实业务面板。
2. 支持：
   - 情绪新增
   - 情绪删除
   - 参考音频上传
   - 关联当前角色/情绪

验收：

1. 情绪管理不再只是标签层面的本地 UI。

#### P2-C Assets 正式表格页

目标：

1. 从桌面 `emotion_assets_panel.py` 提炼成 Web 正式页面或正式子面板。
2. 资产能力必须形成独立、可检索、可筛选、可操作的工作流。

建议 UI：

1. 主表格
2. 右侧详情抽屉
3. 顶部筛选与批量操作栏

验收：

1. 用户可以在 Web 端完成上传、试听、绑定、解绑、备注、删除。

#### P2-D 清理流程对齐

目标：

1. 重做当前缓存/资产清理流程。
2. 与后端接口模型对齐。

验收：

1. 清理行为有明确定义：
   - 清理全部未引用
   - 清理当前筛选结果
   - 清理用户选中项
2. 前后端契约一致。

### 6.3 P2 依赖

依赖 P1 完成 API/Store 收敛设计。

### 6.4 P2 完成标准

1. Voices 闭环成立。
2. Assets 闭环成立。
3. 桌面 `voice_settings.py` 的主流程具备 Web 替代性。

## 7. P3：Workspace 生产闭环

目标：

1. 把桌面 `text_edit.py + task_plan.py` 的核心业务在 WebUI 中收口。
2. 让“脚本 -> 任务 -> 合成 -> 回收结果”成为一条连续工作流。

### 7.1 Workspace 模块覆盖范围

必须覆盖：

1. 脚本编辑
2. 剧本解析
3. 导入任务
4. 行级参数控制
5. 单行运行
6. 批量运行
7. 合成结果试听
8. 结果列表回收
9. 任务保存/加载
10. 音频 merge

### 7.2 任务拆分

#### P3-A 脚本编辑器定型

目标：

1. 明确不再走桌面富文本选区染色模型。
2. 用结构化脚本块承载：
   - role
   - emotion
   - text
   - filter/sfx/break 等附加信息

验收：

1. 脚本编辑器具备长期演进价值，不再是过渡形态。

#### P3-B 任务表字段补齐

目标：

补齐当前缺失字段：

1. `mode`
2. `instruct_text`
3. `seed`
4. 单行运行

验收：

1. Web 任务表的参数能力不低于桌面任务页的核心使用场景。

#### P3-C 批量结果回收与播放修复

目标：

1. 修复 API Key 下 `<audio>` 播放问题。
2. 建立统一试听与回放处理。

验收：

1. 有鉴权和无鉴权两种模式都能正常播放。

#### P3-D 任务持久化

目标：

1. 支持任务计划保存/加载。
2. 明确持久化格式与工程格式的关系。

验收：

1. 用户能中断工作并恢复任务计划。

#### P3-E 音频合并

目标：

1. 为批量结果提供 merge 工作流。
2. 与 Export 能力衔接。

验收：

1. 可对当前批次结果执行合并导出。

### 7.3 P3 依赖

1. P1 收敛完成
2. P2 Voices/Assets 闭环完成

### 7.4 P3 完成标准

1. 桌面 `text_edit.py + task_plan.py` 的主流程可被 Web 替代。
2. 用户无需桌面 GUI 即可完成从文本到结果音频的主链路。

## 8. P4：System + Settings + Export 收口

目标：

1. 解决桌面 `api_page.py` 和 `settings.py` 的主要遗留空白。
2. 让 WebUI 成为真正可独立使用的工作台。

### 8.1 System 模块

保留目标：

1. 健康检查
2. 模型状态
3. GPU/VRAM
4. unload/reload
5. cleanup
6. 连接配置

不建议优先迁的内容：

1. 完整的本地 server 进程生命周期编排
2. 桥接进程控制台式 UI

建议：

1. 先采用“连接型 System 页面”。
2. 仅在产品明确要求本地一体化时，才再评估桥接/服务生命周期迁移。

### 8.2 Settings 模块

目标：

1. 将桌面设置能力按“是否适合 Web”重新分类。

建议分类：

#### 必须进入 Web

1. baseUrl
2. apiKey
3. 当前环境/配置切换
4. 与工作流直接相关的用户偏好

#### 不必进入 Web 首期

1. 本地模型路径
2. 本地输出目录
3. Bridge Python 路径

这些更适合作为部署文档或本地启动脚本问题，而不是 Web 产品首期设置项。

### 8.3 Export 模块

目标：

1. 整理并正式化当前 `ExportPanel`。
2. 明确它是正式一级模块，而不是附属工具。

要求：

1. 工程保存/恢复
2. JSON 导入导出
3. 音频导出
4. SRT 导出

### 8.4 P4 完成标准

1. System 页可支持正式工作流所需的系统控制。
2. Settings 页可支持连接与基础偏好设置。
3. Export 页已纳入正式信息架构。

## 9. P5：App Shell 与重复页面退役

目标：

1. 把当前多 tab 混合架构收敛为正式 App Shell。
2. 删除重复入口和重复实现。

### 9.1 任务

#### P5-A App Shell 重建

目标：

1. 重构 `App.vue`。
2. 从“功能 tab 集合”转为“正式产品导航”。

建议导航：

1. Workspace
2. Voices
3. Assets
4. Library
5. Export
6. System

#### P5-B 重复页面退役

需要逐项决定：

1. 旧 `VoiceManager` 是否保留为中间实现，还是其能力完全吸收到正式页面
2. 旧 `ScriptEditor` 是否保留为实验页，还是其能力吸收到 Workspace
3. `TtsConfigPanel` 是否保留为 System 子模块

原则：

1. 正式产品中每个能力只能有一个入口。

#### P5-C 视觉系统统一

目标：

1. 移除当前多套视觉语言并存的问题。
2. 统一设计 token、图标系统、交互反馈、empty state、dialog、toolbar。

说明：

1. 视觉统一应放在业务闭环之后，不应前置。

### 9.2 P5 完成标准

1. 正式 App Shell 完成。
2. 重复页面退役。
3. WebUI 信息架构稳定。

## 12. 不建议的开发顺序

以下顺序应避免：

1. 先重写 `App.vue` 导航，再去补底层业务
2. 先统一视觉，再去打通 voice/asset 闭环
3. 先做桌面 GUI 同步优化，再说 Web 收口
4. 先做桥接/本地服务复杂运维，再补业务闭环

原因：

1. 这些路径都会让迁移继续发散。

---

## 13. 推荐的近期执行顺序

如果以最近一轮开发作为目标，建议顺序如下：

1. P0 确认边界
2. P1 收敛 API/Store
3. P2 完成 Voices + Assets
4. P3 完成 Workspace
5. P4 收口 System + Export
6. P5 重建 App Shell 并退役重复页面
