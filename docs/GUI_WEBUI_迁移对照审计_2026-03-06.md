# GUI -> WebUI 迁移对照审计

日期：2026-03-06  
仓库：`C:\Users\lilei\Desktop\voice`

## 1. 目的与结论

本文用于回答一个具体问题：

> 如果目标是“把原来的桌面 GUI 功能全部迁移到 WebUI”，当前进行到哪一步？

审计结论：

1. 当前状态不是“桌面 GUI 已基本切完”，而是“桌面 GUI 与 WebUI 并行开发”。
2. WebUI 已具备一个可运行的主流程雏形：`健康检查 -> 拉取 voices -> 编辑脚本/任务 -> 批量合成 -> 模型控制`。
3. 迁移最深的部分在 `web_ui/src/views/pro_workspace/`；但这里的 voice/asset 能力仍有明显缺口。
4. 另有一套通用 WebUI 页面（`VoiceManager` / `TtsConfigPanel` / `ScriptEditor` / `ExportPanel`）实现了部分真实能力，但并没有完整收敛到迁移主线。
5. 桌面 GUI 中最复杂、最成熟的三块仍未等价落地到 WebUI：
   - `voice_settings.py` 为核心的 voice + refs + assets 闭环
   - `api_page.py` 为核心的 API/Bridge 运维面板
   - `settings.py` 为核心的应用/路径/运行参数设置

一句话概括：

> WebUI 目前更接近“已经跑通一条新工作流的 Alpha 版本”，还不是“完成桌面 GUI 全量替换”的阶段。

## 2. 审计范围与判断口径

### 2.1 桌面 GUI 审计范围

以 `ui/main_window.py` 当前导航作为桌面主流程基准：

1. `TextEditInterface`
2. `TaskPlanInterface`
3. `VoiceSettingsInterface`
4. `APIPageInterface`
5. `SettingsInterface`
6. 底部全局动作：`加载模型 / 卸载模型 / 切换主题`

同时把以下桌面子组件视为主流程一部分：

1. `ui/components/emotion_assets_panel.py`
2. `ui/components/voice_refs_sheet.py`
3. `ui/voice_setup_wizard.py`
4. `ui/asset_cleanup_dialog.py`
5. `ui/components/voice_rename_wizard.py`

### 2.2 WebUI 审计范围

Web 端分成两层：

1. 迁移主线候选：`web_ui/src/views/pro_workspace/`
2. 通用工作台：`web_ui/src/components/` 与相关 store/api

### 2.3 状态标签定义

- `已完成`：WebUI 已能独立完成与桌面端等价的用户目标。
- `部分完成`：核心流程已存在，但字段、边角流程或运维能力明显不齐。
- `未开始`：没有可见 WebUI 能力。
- `有接口但前端未接`：后端或 store/client 已具备能力，但 UI 主线没有真正打通。

## 3. 现状总览

## 3.1 桌面端仍然是并行主线

表现：

1. 桌面入口仍是 `main.py`，启动 `QApplication` 和 PyQt 主窗口。
2. `ui/` 下多个主流程文件仍在持续修改。
3. Web 端启动脚本 `StartWebUI.bat` 只是单独起前端开发服务器，不负责替代桌面壳层。

## 3.2 WebUI 当前实际上有两条路线

### 路线 A：Pro Workspace

目标更像“把桌面核心操作台搬到 Web 上”，包括：

1. `ProSystemSettings`
2. `ProVoiceManager`
3. `ProEmotionEditor`
4. `ProScriptEditor`
5. `ProTaskPlanTable`
6. `ProStorageCleanup`

优点：

1. 结构上最贴近桌面 GUI 主流程。
2. 已接入健康检查、拉 voices、批量合成、模型 unload/reload。

问题：

1. voice CRUD 仍有本地假实现。
2. asset 管理还是占位。
3. 若开启 API Key，部分播放链路会出问题。

### 路线 B：通用工作台

包括：

1. `TtsConfigPanel`
2. `VoiceManager`
3. `ScriptEditor`
4. `ExportPanel`
5. `ChatPanel`
6. 资源库相关页面

优点：

1. 某些真实能力比 Pro Workspace 更完整。
2. 例如 `VoiceManager` 已接真实 voice CRUD。

问题：

1. 信息架构更偏“新产品工作台”，不是按桌面 GUI 一对一迁移。
2. 功能散落在多个 tab，不利于做桌面功能平移。
3. 有能力但没形成“迁移闭环”。

## 5. 关键阻塞项与设计债

## 5.1 两套 Web 能力分裂

现象：

1. `ProWorkspace` 更像迁移主线，但 CRUD/asset 不完整。
2. 通用 `VoiceManager` / `VoicesStore` 更接近真实 CRUD，但不在迁移主线里。

影响：

1. 功能已存在，却不能算迁移完成。
2. 后续容易重复造轮子。

建议：

1. 先确定 `ProWorkspace` 是否为唯一迁移主线。
2. 如果是，则把 `VoicesStore + CosyVoiceClient` 的真实 CRUD 能力并入 Pro 路线。

## 5.2 voice/asset 闭环未收口

现象：

1. Pro 路线新建/删除 voice 仍是本地假数据。
2. 情绪编辑器仍是占位上传区。
3. 资产 store 已有上传/删除/绑定动作，但没被整合为完整 UI。

影响：

1. WebUI 还不能替代桌面 `voice_settings.py`。
2. 这是最核心的产品阻塞项。

## 5.3 缓存清理接口不匹配

现象：

1. `ProStorageCleanup.vue` 直接调用 `cleanupStorage()`。
2. `ProApiClient.cleanupStorage()` 调的是 `/api/v2/assets/audio/cleanup`，但没有提交 `asset_ids`。
3. 后端该接口要求 `asset_ids` 必填。

影响：

1. 该功能大概率当前不可用。

建议：

1. 先决定“Web 清理”是全量清理未引用资产，还是显式选择资产后再清理。
2. 再对齐前后端请求模型。

## 5.4 API Key 开启后的音频播放问题

现象：

1. `ProApiClient` 已明确写了：受保护音频路由不能直接给 `<audio src>`。
2. `ProTaskPlanTable.vue` 仍直接使用 `row.audio_url`。

影响：

1. 一旦启用 `X-API-Key`，批量结果播放存在失败风险。

建议：

1. 将任务表播放改为 `getAuthedAudioUrl()` -> Blob URL。

## 5.5 设置与运维能力缺位

现象：

1. Web 没有桌面设置页的路径/运行参数配置。
2. Web 没有桌面 API 页的服务/桥接运维。

影响：

1. 即使生成链路可用，也无法完全替代桌面端作为“本机控制台”。

## 7. 下一步开发建议

## 7.1 先做架构选择，不要继续双线扩散

建议先明确一个判断：

1. `ProWorkspace` 是否就是最终 Web 迁移主线？

如果答案是“是”，建议：

1. 停止在通用 `VoiceManager` 上继续加迁移型功能。
2. 把已经成熟的 `VoicesStore` / `CosyVoiceClient` 迁入 Pro 路线。

如果答案是“否”，建议：

1. 明确放弃“桌面页面映射”思路，改写一版新的 Web 信息架构文档。

## 7.2 最小可用迁移闭环（建议优先级）

### M1：把 voice 主链路打通

目标：

1. Pro 路线接真实 voice 创建/编辑/删除
2. 能真实拉取并修改 voice 数据
3. 能在 Web 端完成基本 voice 管理，不依赖桌面

### M2：把 refs/assets 闭环打通

目标：

1. 资产列表
2. 上传
3. 绑定/解绑
4. 试听
5. 备注编辑
6. 清理未引用资产

这是桌面迁移的第一关键里程碑。

### M3：补齐任务页高级能力

目标：

1. 单行运行
2. mode / instruct / seed 字段
3. 任务保存/加载
4. 音频合并
5. 受鉴权音频播放修复

### M4：补齐运维与设置

目标：

1. 最少补一个 Web 设置页
2. 决定 API/Bridge 运维是否迁移

如果不迁：

1. 文档中应明确“Web 端依赖外部 API 服务，不承担本机运维功能”。

如果迁：

1. 需要新增独立“系统/运维”页，而不是继续塞进 Pro 顶栏。

## 9. 最终建议

当前不建议直接开始“零散补洞”。

更合理的顺序是：

1. 先选定唯一 Web 迁移主线。
2. 先完成 `voice + asset + task` 的最小业务闭环。
3. 再决定是否迁移“桌面运维页”和“富文本高级编辑器”。

否则会继续出现这种状态：

1. 某项能力后端有
2. store 里也有
3. 某个次级 tab 里也许能用
4. 但迁移主线 UI 仍然不能替代桌面 GUI

这会持续拉高维护成本，也会让“迁移完成度”一直看不清。
