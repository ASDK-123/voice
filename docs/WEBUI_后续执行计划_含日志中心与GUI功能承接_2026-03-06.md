## 3. 最新产品决策

基于当前代码状态，本项目从今天开始执行以下新增决策。

### D1. 允许继续增加必要的正式 Tab

允许，但必须同时满足以下条件：

1. 该能力是稳定领域，不是临时堆功能。
2. 该能力有清晰 owner，不与现有正式页职责重叠。
3. 该能力具有较高使用频率，或是系统级能力入口。
4. 该能力无法合理塞入现有页面而不造成再次过载。
5. 该 Tab 使用简体中文命名，不使用 emoji。

### D2. “日志”升格为正式一级 Tab

决定：

1. 新增一级 Tab：`日志`
2. `日志` 不放进 `系统` 的二级折叠区
3. `日志` 作为正式、长期存在的领域页面，而不是调试临时页

原因：

1. 实时日志是桌面 GUI 已有能力，属于缺失的正式承接项。
2. 日志涉及运行态可观察性，不应被埋在配置页面里。
3. 日志跨越：
   - 服务状态
   - 模型状态
   - 请求访问
   - 崩溃排障
   - 本地桥接
   这已经超出普通设置页的合理边界。

### D3. 继续以 WebUI 承接 GUI 能力，但不做 1:1 桌面复制

原则不变：

1. 保留业务闭环
2. 重做不适合 Web 的桌面交互
3. 把“桌面 API 服务管理页”的核心价值拆分到：
   - `系统`
   - `日志`
   两个正式页中

## 5. 允许继续增加 Tab 的边界规则

后续如果继续新增正式 Tab，必须遵守以下规则。

### R1. 一级 Tab 的准入门槛

只允许在以下情况新增一级 Tab：

1. 已经形成稳定领域对象和独立数据源
2. 需要用户直接抵达，而不是深层操作
3. 已有页面会因该能力过载而继续恶化
4. 该页面能够长期存在，不是一次性迁移工具

### R2. 不应新增一级 Tab 的情况

以下情况不应新增一级 Tab：

1. 只是某个页面的高级设置
2. 只是单个弹窗或单个向导
3. 只是开发调试临时面板
4. 只是某个领域的筛选视图变化

### R3. 当前允许新增但不立即启用的候选领域

当前只保留为候选，不立刻进入一级导航：

1. `服务`
   - 仅当 API 生命周期控制、本地桥接、本地进程编排继续膨胀时，才考虑从 `系统` 中拆出
2. `迁移`
   - 仅当 legacy 导入、配置迁移、桌面退场引导形成长期需求时，才考虑单列

结论：

1. 当前立即要新增的是 `日志`
2. 其他候选领域暂不加一级 Tab

## 7. 日志中心（新增一级 Tab）执行方案

## 7.1 日志中心的目标

日志中心必须同时解决四类问题：

1. WebUI 用户看不到正在发生什么
2. 桌面 GUI 已有运行日志能力，但 WebUI 没有
3. 后端已有日志产物，但没有浏览器消费接口
4. 日志、崩溃、访问事件分散在文件中，排障路径不连续

## 7.2 日志中心的范围

### 必须支持

1. 实时显示应用日志
2. 查看 API 访问日志
3. 查看崩溃日志摘要
4. 按级别筛选
5. 按来源筛选
6. 按关键字搜索
7. 自动滚动 / 暂停滚动
8. 复制 `request_id`
9. 导出诊断包
10. 在 API Key 场景下正常工作

### 首版可暂缓

1. 多人协作日志权限模型
2. 复杂时间轴可视化
3. 远端日志归档策略
4. 浏览器端全文索引

## 7.3 日志中心的数据源

首版统一围绕以下日志源设计：

1. `data/logs/app.log`
2. `data/logs/access.jsonl`
3. `data/logs/crash.log`
4. `data/logs/webui_local_bridge_api.log`（本地启动桥日志，新增接入）

说明：

1. `app.log` 用于人读运行日志
2. `access.jsonl` 用于请求级事件与 `request_id` 排查
3. `crash.log` 用于异常和崩溃定位
4. `webui_local_bridge_api.log` 用于本机模式下 API 启动失败排查

## 7.4 日志中心的页面结构

建议布局：

1. 顶部摘要区
   - 当前服务状态
   - 当前模型状态
   - 当前日志源
   - 当前过滤条件
2. 工具栏
   - 日志源切换
   - 级别筛选
   - 搜索框
   - 自动滚动开关
   - 暂停/恢复
   - 刷新
   - 导出诊断包
3. 主列表区
   - 时间
   - 级别
   - 模块
   - 事件/消息
   - `request_id`
4. 右侧详情抽屉
   - 完整消息
   - 原始 JSON
   - 关联字段
   - 复制按钮

## 7.5 日志中心的交互规则

1. 默认进入“实时日志”
2. 默认开启自动滚动
3. 用户上滑查看历史记录时自动暂停滚动
4. 重新点击“回到底部”恢复自动滚动
5. 新日志到达时不闪屏、不跳布局
6. 所有筛选都应保留在当前会话
7. 危险操作只允许“清空当前浏览器视图”，不允许从 Web 直接删除服务器日志文件

## 7.6 日志中心的设计规则

遵守以下规则：

1. 不使用 emoji 作为等级图标
2. 使用统一 SVG 图标集
3. 颜色仅用于辅助，不作为唯一状态表达
4. 支持键盘聚焦与复制
5. 列表密度要高，但仍保持可读性
6. 支持 `prefers-reduced-motion`
7. 操作按钮最小点击区域不低于 `44px`

推荐视觉基线：

1. 页面仍沿用浅色系统
2. 重点状态色：
   - 信息：蓝
   - 成功：绿
   - 警告：橙
   - 错误：红
3. 列表字体优先使用等宽字体显示：
   - `JetBrains Mono`
   - 或系统等宽字体

## 7.7 日志后端接口方案

浏览器不能直接读取本地日志文件，因此必须新增正式接口。

### 第一阶段：先做稳定可交付版（轮询 Tail）

新增建议接口：

1. `GET /api/v2/pro/logs/sources`
   - 返回可用日志源与可见性
2. `GET /api/v2/pro/logs/tail`
   - 参数：
     - `source=app|access|crash|local_bridge`
     - `cursor=...`
     - `limit=...`
     - `level=...`
     - `q=...`
   - 返回：
     - `items`
     - `next_cursor`
     - `truncated`
3. `GET /api/v2/pro/logs/file`
   - 获取原始文件下载
4. `POST /api/v2/pro/logs/diagnostic-bundle`
   - 触发诊断包导出，或返回现有脚本结果

理由：

1. 首版交付风险最低
2. 与现有 Flask 结构兼容
3. 可以先满足“实时显示运行日志”的核心需求

### 第二阶段：补实时体验增强版（SSE）

新增建议接口：

1. `GET /api/v2/pro/logs/stream`
   - 使用 Server-Sent Events
   - 首期仅支持：
     - `app`
     - `access`
2. `crash` 与 `local_bridge` 保持轮询即可

理由：

1. `access.jsonl` 与 `app.log` 是高频日志源
2. SSE 比 WebSocket 更适合单向日志推送
3. 可以在首版上线后再补，不阻塞交付

## 7.8 日志接口的数据格式

统一输出结构：

```json
{
  "items": [
    {
      "id": "log_001",
      "source": "app",
      "timestamp": "2026-03-06T17:00:00+08:00",
      "level": "INFO",
      "module": "api",
      "event": "SYN_DONE",
      "message": "合成完成",
      "request_id": "req_xxx",
      "fields": {
        "voice_id": "胡桃#default",
        "duration_ms": 820
      },
      "raw": "{...}"
    }
  ],
  "next_cursor": "cursor_xxx",
  "truncated": false
}
```

要求：

1. `app.log` 需要在后端解析为统一结构
2. `access.jsonl` 可直接转换为标准项
3. `crash.log` 至少要抽出：
   - 时间
   - 级别
   - 模块
   - message
4. `request_id` 缺失时返回空字符串

## 7.9 日志接口权限规则

1. 如果启用 `V2_API_KEY`，日志接口必须受保护
2. `local_bridge` 日志默认仅本机模式暴露
3. 远端服务不应默认暴露本地桥接日志
4. 生产模式下可通过配置关闭 `crash` 原文输出，仅保留摘要

## 9. 本轮建议的直接开发顺序

如果从下一次实际开发开始，推荐顺序如下：

### 第一优先级

1. 新增 `日志` 一级 Tab
2. 先做日志后端 tail 接口

1. 这是当前最明确的缺口

### 第二优先级

2. 把桌面 `APIPage` 的高价值能力分拆进 `系统 + 日志`

### 第三优先级

1. 补音色/资产/剧本中的高级入口
2. 继续承接剩余 GUI 主流程

### 第四优先级

1. 收敛 API / Store
2. 清理 legacy 入口

## 12. 最终执行建议

一句话建议：

> 后续 WebUI 开发应从“继续拆正式领域页”升级为“补齐系统级可观察性与 GUI 缺失能力”；  
> 当前最应该立即推进的新增项不是再做视觉样式，而是把 `日志中心` 做成正式一级 Tab，并以此为抓手承接桌面 `APIPage` 的核心价值。

对应到执行上，就是：

1. 立即接受“允许继续增加必要 Tab”的策略，但必须遵守准入规则
2. 立即把 `日志` 纳入正式一级导航
3. 先做日志后端接口，再做日志中心页面
4. 再把桌面 `API 服务管理` 的剩余能力拆入 `系统 + 日志`
5. 最后再统一 API / Store，并推进桌面 GUI 退场

这条路径最符合当前项目的真实状态：

1. 主工作流已基本可用
2. 产品壳层已开始成形
3. 真正缺的不是再加一堆功能，而是把系统可观察性和正式边界补齐
