## 1. 文档目的

这份文档回答五个问题：

1. WebUI 现在已经能做什么
2. 下一阶段应该怎么拆页面，而不是继续把功能堆进一个界面
3. 哪些现有模块应该直接复用，避免重复造轮子
4. 如何在保持简体中文的前提下，按苹果式设计哲学重构 WebUI
5. 如何在推进体验重构的同时保证后续可维护性

本文只给出后续详细计划方案，不要求立即改代码。

---

## 2. 硬约束

后续所有 WebUI 重构必须遵守以下约束：

1. **界面语言统一为简体中文**
2. **允许新增正式 Tab，不再让单一页面承载过多功能**
3. **优先复用现有 WebUI 已落地能力，不重复开发同类页面**
4. **产品收口优先于视觉炫技**
5. **维护成本优先于短期堆功能**
6. **桌面 GUI 仍作为过渡期回退入口，但不再作为新功能主线**

---

## 3. 当前 WebUI 已有能力盘点

当前 WebUI 已经不是空壳，而是已经形成了多条可运行能力线。后续规划必须建立在“吸收和收口”上，而不是“推倒重来”。

## 3.1 已经可运行的主线能力

### A. 主工作站能力

当前 `ProWorkspace` 路线已经具备：

1. 健康检查与心跳
2. 模型加载状态显示
3. GPU / 显存状态显示
4. 模型重载
5. 模型卸载
6. 未使用资产清理
7. 音色列表加载
8. 音色创建 / 编辑 / 删除
9. 音色情绪分组
10. 音色编译
11. 参考音频上传 / 绑定 / 解绑 / 删除
12. 资产列表与 `linked / unused` 过滤
13. 资产试听
14. 资产备注 / transcript 编辑
15. 剧本片段导入任务计划
16. 任务计划编辑
17. 批量合成
18. 单行运行
19. `mode / instruct_text / seed` 参数控制
20. API Key 场景下结果播放
21. 任务草稿恢复
22. 任务计划 JSON 导入 / 导出
23. 批量结果 merge 导出

结论：

1. `Workspace / Voices / Assets / Task / System` 的主工作流已经具备基础替代能力。
2. 这部分不应重做，只应拆分、命名、收口和统一风格。

### B. 通用旧页面中已经成熟的能力

当前通用 Web 页并非都应废弃，其中一些能力已经成熟，应直接吸收：

1. `ScriptEditor`：
   - 原文输入
   - 角色管理
   - 角色音色绑定
   - AI 深度分析
   - 脚本行编辑
   - 连播
   - 音频逐行生成
2. `ChatPanel`：
   - Prompt 生成
   - LLM 结果预览
   - 分析结果应用到脚本
3. `PromptConfigPanel`：
   - 自定义 Prompt 模板
   - Prompt 变量说明
4. `LlmConfigPanel`：
   - LLM 配置管理
   - 模型列表查询
5. `TtsConfigPanel`：
   - TTS 后端配置
   - API Key 配置
6. `ExportPanel`：
   - 浏览器本地保存 / 加载
   - 工程 JSON 导入 / 导出
   - 音频导出
   - SRT 导出
7. `SfxLibrary / BgmLibrary / TimbreLibrary / FilterLibrary`：
   - 资源库型能力已存在

结论：

1. `分析 / 资源库 / 导出 / 配置` 这些能力都已经有现成页面。
2. 当前问题不是“没有”，而是“入口分裂、命名不正式、体验不一致、状态不统一”。

### C. 工程保障能力

当前还已经具备：

1. `npm run build`
2. 最小 smoke 流程
3. WebUI-first README
4. WebUI-first 启动入口

这意味着后续可以在不依赖桌面 GUI 的前提下继续推进 WebUI 主线。

## 3.2 当前真正的问题

当前 WebUI 最大的问题不是功能不足，而是产品结构和工程结构还处于过渡态。

### A. 产品结构问题

1. Tab 命名中英文混杂
2. 仍存在 emoji 作为主图标语义
3. `ProWorkspace` 承载过多功能
4. 历史页与正式页并行
5. 用户不知道哪一个入口才是正式入口

### B. 设计风格问题

1. `ProWorkspace` 使用独立暗色 Bento 风格
2. 其他页面偏浅色后台工具风格
3. 同一产品里出现两套视觉语言
4. 中文界面尚未统一

### C. 可维护性问题

1. API 仍有双轨：
   - `pro_client.ts`
   - `cosyvoice.ts`
2. Store 仍有双轨：
   - `pro_voice / pro_task / pro_system`
   - `voices / project / tts`
3. 同一领域存在重复页面：
   - `ProVoiceManager`
   - `VoiceManager`
4. 导出、脚本、分析能力分散在不同区域

结论：

1. 下一步不应该再继续给 `ProWorkspace` 塞新功能。
2. 下一步应该做“正式信息架构重构”。

---

## 4. 后续重构的总策略

一句话策略：

> 不重写已有能力，而是把现有能力按正式模块重编排；先统一入口和命名，再逐步统一 store 和 API。

后续重构顺序必须是：

1. 先确定正式中文信息架构
2. 再新增正式 Tab 入口
3. 再把已有组件吸收到各正式 Tab
4. 再清理 legacy 入口
5. 最后做深层 API / Store 收敛与桌面 GUI 退场

## 5. 苹果式设计哲学在本项目中的落地方式

这里的“苹果式设计哲学”不是照搬 Apple 官网视觉，而是吸收其核心原则：

1. **清晰**
2. **聚焦**
3. **一致**
4. **直接**
5. **克制**
6. **高质量默认值**

将其转成 WebUI 的执行规则如下。

## 5.1 设计原则

### P1. 一个页面只服务一个主目标

例子：

1. 音色页只负责音色
2. 资产页只负责参考音频资产
3. 导出页只负责导入导出与结果导出
4. 系统页只负责连接、模型、运行状态

禁止再让单一页面同时长期承担：

1. 系统控制
2. 音色管理
3. 剧本编辑
4. 任务运行
5. 导出操作

### P2. 默认界面要安静

首页不应是密集表单墙，而应是“状态 + 最近任务 + 快速进入”。

### P3. 高级功能采用渐进展开

高级参数不消失，但不默认压在主视图上：

1. `instruct_text`
2. `seed`
3. Prompt 模板
4. 资产 transcript / note
5. 高级导出选项

它们应进入：

1. 折叠面板
2. 抽屉
3. 二级 Tab
4. “高级设置”区

### P4. 中文优先，不做中英混排主导航

要求：

1. 一级 Tab 全部使用简体中文
2. 二级标题全部使用简体中文
3. 按钮、空态、错误、确认文案全部使用简体中文
4. 技术字段允许保留括号补充英文，例如：
   - 随机种子（Seed）
   - 指令文本（Instruct Text）

### P5. 统一图标策略

要求：

1. 不再使用 emoji 作为正式导航图标
2. 使用 Heroicons 或 Lucide
3. 危险操作必须有明确颜色与确认动作

### P6. 风格统一采用“浅色、克制、专业”

推荐视觉基线：

1. 主背景：`#F5F5F7`
2. 卡片背景：`#FFFFFF`
3. 主文字：`#1D1D1F`
4. 次文字：`#6E6E73`
5. 强调色：`#0071E3` 或相近系统蓝
6. 成功色：`#34C759`
7. 警告色：`#FF9F0A`
8. 危险色：`#FF3B30`

不建议继续扩张：

1. 紫色 AI 默认风格
2. 重暗色孤岛式工作区
3. 大量发光和毛玻璃叠加

### P7. 字体与排版以简体中文可读性为最高优先级

推荐：

1. 标题：`Noto Sans SC`
2. 正文：`Noto Sans SC`

排版要求：

1. 正文最小 `14px`
2. 重要操作区 `15px-16px`
3. 行高 `1.5` 左右
4. 表格型工作区优先保证密度和对齐

### P8. 动效只用于反馈，不用于炫耀

要求：

1. 微动效时长控制在 `150ms - 250ms`
2. 优先使用 `opacity / transform`
3. 支持 `prefers-reduced-motion`

## 6. 建议的正式信息架构

基于当前已实现能力、用户的“不要一个页面承载太多功能”要求，以及可维护性约束，建议正式改为 8 个一级 Tab。

## 6.1 一级 Tab 方案

### 1. 工作台

定位：

1. 首页
2. 状态总览
3. 最近任务
4. 快捷入口

不承担：

1. 大量编辑工作
2. 大量表格录入

### 2. 剧本

定位：

1. 原文输入
2. 角色管理
3. AI 分析
4. 脚本结果编辑
5. 导入任务计划

建议二级结构：

1. 原文
2. 分析
3. 脚本行

### 3. 任务

定位：

1. 批量任务编辑
2. 单行运行
3. 批量运行
4. 结果试听
5. 任务计划保存 / 导入 / 导出
6. merge 导出

### 4. 音色

定位：

1. 音色列表
2. 新建 / 编辑 / 删除
3. 情绪配置
4. 编译
5. 角色分组

### 5. 资产

定位：

1. 参考音频资产列表
2. 上传
3. 试听
4. 绑定 / 解绑
5. transcript / note 编辑
6. unused 清理

### 6. 资源库

定位：

1. 音效
2. BGM
3. Timbre
4. Filter

建议二级结构：

1. 音效
2. 背景音乐
3. 音色素材
4. 滤镜

### 7. 导出

定位：

1. 工程保存 / 加载
2. 工程导入 / 导出
3. 音频导出
4. SRT 导出
5. 结果文件导出

### 8. 系统

定位：

1. TTS 后端连接配置
2. API Key 配置
3. LLM 配置
4. Prompt 模板
5. 健康状态
6. 模型控制
7. 存储清理

## 6.2 一级 Tab 的来源映射

后续不建议从零重做页面，而应先做“路由和壳层重编排”，映射如下。

| 正式 Tab | 优先复用的现有模块 | 后续处理 |
|---|---|---|
| 工作台 | `ProSystemSettings`、`ProTaskPlanTable` 的摘要视图 | 新增轻量首页，不再把完整编辑器放首页 |
| 剧本 | `ScriptEditor`、`ChatPanel`、`PromptConfigPanel`、`ProScriptEditor` | 先复用，后统一到正式剧本域 |
| 任务 | `ProTaskPlanTable` | 直接升格为正式任务页 |
| 音色 | `ProVoiceManager`、`ProVoiceWizardModal`、`ProEmotionEditor` | 直接升格为正式音色页 |
| 资产 | `ProAssetsPanel`、`ProStorageCleanup` | 将弹窗面板升级为正式页面 |
| 资源库 | `SfxLibrary`、`BgmLibrary`、`TimbreLibrary`、`FilterLibrary` | 作为正式资源库模块保留 |
| 导出 | `ExportPanel` + `pro_task.exportMergedAudio` | 统一成正式导出中心 |
| 系统 | `TtsConfigPanel`、`LlmConfigPanel`、`ProSystemSettings` | 合并为正式系统页 |

结论：

1. 真正需要“新建”的主要是外层导航壳和部分页面布局。
2. 真正需要“重写”的模块并不多。

## 7. 模块归属与避免重复造轮子的策略

后续必须明确“谁是正式 owner”，否则页面一拆，重复状态会更多。

## 7.1 领域 owner 约束

### A. 音色域

正式 owner：

1. `ProVoiceManager`
2. `useProVoiceStore`

待退役：

1. `VoiceManager`
2. `useVoicesStore` 中的正式音色管理职责

短期策略：

1. 旧 `VoiceManager` 只作为参考实现和过渡入口
2. 不再继续增强旧音色页

### B. 任务域

正式 owner：

1. `ProTaskPlanTable`
2. `useProTaskStore`

说明：

1. 任务计划、批量运行、合成状态、结果播放都应继续收敛在 `pro_task`

### C. 系统域

正式 owner：

1. `useProSystemStore`
2. `useTtsStore`

短期策略：

1. 连接配置继续用 `tts`
2. 健康、模型状态、模型控制继续用 `pro_system`
3. 中期再决定是否并成单一 `system` store

### D. 分析域

正式 owner：

1. `useLlmStore`

直接复用：

1. `LlmConfigPanel`
2. `PromptConfigPanel`
3. `ChatPanel`

### E. 资源库域

正式 owner：

1. `useLibrariesStore`

直接复用：

1. `SfxLibrary`
2. `BgmLibrary`
3. `TimbreLibrary`
4. `FilterLibrary`

### F. 导出域

短期正式 owner：

1. `ExportPanel`
2. `useProTaskStore.exportMergedAudio`

中期目标：

1. 抽成统一 `export` 域

## 7.2 页面复用策略

后续重构推荐采用三段法：

### 第一步：壳层重组

做什么：

1. 新建正式中文 Tab
2. 旧组件原样挂进去

目的：

1. 先把产品结构理顺
2. 先把“一个页面太重”的问题解决

### 第二步：组件吸收

做什么：

1. 把旧页面中成熟能力逐步吸入正式模块
2. 把重复页面标记为 legacy

### 第三步：状态和接口收敛

做什么：

1. 收敛 API
2. 收敛 store
3. 删除重复逻辑

## 8. 详细实施阶段

后续实施建议分为 6 个阶段，延续中期报告中的节奏，但把重点改成“信息架构 + 中文化 + 维护性”。

## 阶段 A：正式导航与中文基线

目标：

1. 建立正式中文一级 Tab
2. 去掉中英混杂的主导航
3. 停止继续扩张 `ProWorkspace`

任务：

1. 一级 Tab 改为：
   - 工作台
   - 剧本
   - 任务
   - 音色
   - 资产
   - 资源库
   - 导出
   - 系统
2. 去掉主导航中的 emoji
3. 为所有一级 Tab 定义中文标题、副标题、空态文案、错误文案
4. 标记所有历史入口为 `Legacy` 或移出一级导航

验收：

1. 用户首次打开 WebUI 时不会再看到混合式旧导航
2. 首页和一级导航全部是简体中文

## 阶段 B：按 Tab 拆出正式页面

目标：

1. 让单页不再过载
2. 把弹窗和旧组合页升级为正式页面

任务：

1. 工作台只保留总览与快速入口
2. 任务从 `ProWorkspace` 中拆成正式任务页
3. 音色从 `ProWorkspace` 中拆成正式音色页
4. 资产从弹窗升级为正式资产页
5. 剧本整合原文、分析、脚本行
6. 系统页整合连接配置、模型控制、LLM 配置、Prompt 模板

验收：

1. 工作台不再承担完整录入工作
2. 音色、资产、任务都能独立打开与完成主流程

## 阶段 C：导出与资源库正式化

目标：

1. 完成 `P4 Export / System / Settings`
2. 不再让导出逻辑散落在多个区域

任务：

1. 以 `导出` 作为唯一正式出口
2. 收拢：
   - 工程导入 / 导出
   - 本地保存 / 加载
   - 批量 merge 导出
   - SRT 导出
3. 以 `资源库` 作为唯一正式素材入口
4. 明确资源库与资产页分工：
   - 资产：参考音频资产
   - 资源库：音效 / BGM / 滤镜 / Timbre

验收：

1. 用户能明确分辨“参考音频资产”和“音效/BGM 资源库”
2. 导出能力有唯一正式入口

## 阶段 D：API / Store 收敛

目标：

1. 降低维护成本
2. 避免多 Tab 后重复逻辑继续膨胀

任务：

1. 定义统一 API 底座
2. 逐步合并 `pro_client.ts` 与 `cosyvoice.ts`
3. 明确每个领域的权威 store
4. 逐步迁走旧 `voices / project` 中与正式模块重复的职责

验收：

1. 每个领域都有唯一权威 store
2. 新页面不再跨两套 store 取同类数据

## 阶段 E：视觉统一与交互打磨

目标：

1. 统一产品气质
2. 让 WebUI 像一个产品，而不是多个试验页拼在一起

任务：

1. 统一浅色系统主题
2. 统一卡片、表格、抽屉、弹窗、按钮样式
3. 统一状态色、焦点态、危险态
4. 统一中文字段命名
5. 统一错误反馈和成功提示

验收：

1. 不再存在“某一页像另一个产品”的视觉断层
2. 中文界面文案风格统一

## 阶段 F：退场签收

目标：

1. 推进 `G1 -> G2`
2. 为桌面 GUI 冻结做准备

任务：

1. 真实后端回归：
   - 无鉴权
   - 有鉴权
   - 新建音色
   - 上传资产
   - 绑定资产
   - 批量合成
   - 导出工程
   - 导出音频
2. 补强 smoke / E2E
3. 更新 README 和迁移说明
4. 明确桌面 GUI 冻结通知

验收：

1. 满足 `G1` 门槛
2. 接近或满足 `G2` 的功能与质量门槛

## 9. 近期最推荐的执行顺序

如果只看下一步，不建议直接做大规模视觉改版。建议按下面顺序推进。

### 第一优先级

1. 定正式中文 Tab
2. 把 `任务 / 音色 / 资产 / 导出 / 系统` 拆成独立正式页

原因：

1. 这一步收益最大
2. 对现有功能破坏最小
3. 能立刻解决“单页过重”和“入口混乱”

### 第二优先级

1. 收口 `系统 + 导出`
2. 完成 `P4`

原因：

1. 这是桌面 GUI 退场前的硬门槛

### 第三优先级

1. 做 `API / Store` 收敛

原因：

1. 页面一旦拆完，不统一数据层，维护成本会持续上升

### 第四优先级

1. 统一视觉系统
2. 清理 legacy 入口

## 10. 当前不建议做的事

1. 不建议继续把新能力优先塞进 `ProWorkspace`
2. 不建议重新写一套全新的音色页、资产页、导出页
3. 不建议先做大规模视觉炫技改版
4. 不建议立即删除桌面 GUI
5. 不建议在正式 owner 确定前同时增强旧页和新页

## 11. 最终建议

一句话建议：

> 后续 WebUI 应从“功能聚合页”转向“正式产品结构”，核心工作不是重写能力，而是把已经成熟的能力按简体中文多 Tab 产品架构重新编排，并在此基础上逐步完成 API / Store 收敛。

对当前项目来说，最正确的下一步不是“再往主工作站里塞功能”，而是：

1. 先把正式中文导航壳搭起来
2. 先让音色、资产、任务、导出、系统各有正式入口
3. 再做深层统一和桌面 GUI 退场

这条路径最符合：

1. 中期方案的推进节奏
2. 不重复造轮子的要求
3. 简体中文产品化要求
4. 苹果式“清晰、克制、聚焦”的设计哲学
5. 项目长期可维护性
