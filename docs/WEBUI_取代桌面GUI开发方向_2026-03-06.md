# WebUI 取代桌面 GUI 开发方向

日期：2026-03-06  
适用范围：`C:\Users\lilei\Desktop\voice`  
前置文档：`docs/GUI_WEBUI_迁移对照审计_2026-03-06.md`

## 1. 决策结论

本项目后续应明确采用以下方向：

> 以 WebUI 作为唯一产品化前端，围绕桌面 GUI 的核心业务能力做 Web 原生重构；  
> 桌面 GUI 进入冻结态，只保留必要维护，最终退出主线。

这不是“把 PyQt 页面逐页翻译成 Vue 页面”，而是：

1. 保留桌面 GUI 的核心业务闭环。
2. 放弃桌面专属、浏览器不适合的交互模型。
3. 基于现有 WebUI 做架构收敛，形成一个单一、可维护、可扩展的 Web 工作台。

---

## 2. 为什么要这样做

## 2.1 当前问题

当前仓库已经出现三种并存状态：

1. 桌面 GUI 仍在持续开发。
2. `ProWorkspace` 正在承担“迁移主线”的角色，但功能还不完整。
3. 通用 Web 工作台又单独实现了一部分真实能力，导致功能重复和主线不清。

继续这样并行开发，结果只会是：

1. 同一个业务能力写两到三套。
2. 用户路径混乱，不知道哪个页面才是正式入口。
3. 任何一个功能改动都要做双份维护。
4. “迁移完成度”永远无法收口。

## 2.2 WebUI 作为终局的好处

1. 前后端职责更清晰，产品更容易拆分和部署。
2. UI 技术栈统一到 Vue 3 + Pinia + Vite，研发效率更高。
3. 更容易加入 Playwright/E2E 自动化。
4. 更容易扩展远程部署、多端访问、项目存储、账号体系等未来能力。
5. 可以逐步把桌面端的“本地工具型思维”升级成“工作站型产品思维”。

---

## 3. 产品目标重定义

## 3.1 目标不是复刻桌面，而是做一套 Web 工作站

WebUI 的终局应定义为：

> 一个围绕“剧本解析 -> voice/asset 管理 -> 批量合成 -> 导出交付 -> 系统控制”的 TTS 生产工作站。

因此，未来的 WebUI 应具备以下五个主域：

1. `Workspace`
   - 剧本编辑
   - 任务计划
   - 批量合成
   - 单段试听 / 顺序播放
2. `Voices & Assets`
   - voice 配置
   - 情绪变体
   - 参考音频资产
   - 绑定 / 解绑 / 试听 / 备注 / 清理
3. `Library`
   - SFX / BGM / Filter / Timbre
4. `Export`
   - 工程保存 / 导入 / 导出
   - 音频导出
   - 字幕导出
5. `System`
   - 健康检查
   - 模型状态
   - unload / reload
   - 缓存清理
   - 部署与连接设置

## 3.2 什么算“核心业务能力”

桌面 GUI 中必须保留并迁入 WebUI 的，不是所有交互细节，而是这些闭环：

1. 文本到任务的生产闭环
2. voice 到 ref assets 的管理闭环
3. 批量合成与结果回收闭环
4. 系统状态与模型控制闭环
5. 工程保存、导入、导出闭环

只要这五条闭环都在 WebUI 上成立，桌面 GUI 就可以退出主线。

---

## 4. 核心原则

## 4.1 业务上保留，交互上重构

后续迁移不应坚持“桌面什么样，Web 就什么样”。

建议的判断标准：

- 如果桌面功能解决的是业务问题，就保留。
- 如果桌面功能只是 PyQt 时代的交互实现，就允许重做。

### 应保留的能力

1. voice 配置与情绪管理
2. refs / assets 上传、试听、绑定、解绑、备注、清理
3. 任务计划、批量合成、行级参数控制
4. 模型状态、显存释放、健康检查
5. 导出、导入、项目存储

### 不应强行 1:1 复制的能力

1. 富文本选区染色分段
2. 右键菜单驱动的大量桌面快捷操作
3. “打开本地文件夹”类桌面专属入口
4. 依赖桌面壳层生命周期的 UI 编排
5. 纯桌面运维思路的“嵌入式 API 控制台”

## 4.2 单一主线，不再双轨前端

后续必须只有一个正式 Web 主线。

建议：

1. 以 `ProWorkspace` 为最终产品骨架。
2. 把通用 Web 工作台里已经成熟的真实能力吸收进来。
3. 完成吸收后，逐步退役“重复功能 tab”。

原因：

1. `ProWorkspace` 更接近桌面 GUI 的主流程。
2. 它已经具备系统状态、voice 面板、脚本编辑、任务表的工作站形态。
3. 比起继续维护两套 UI，它更适合作为唯一入口。

## 5. 目标信息架构

建议将 WebUI 最终收敛为以下页面结构，而不是继续把所有能力堆在当前 `App.vue` tab 上。

### 1. `Workspace`

职责：

1. 剧本编辑
2. 剧本解析
3. 导入任务
4. 行级参数控制
5. 批量合成
6. 结果试听与回放

### 2. `Voices`

职责：

1. voice 列表与 CRUD
2. 角色与情绪分组
3. prompt/ref 配置
4. 预编译
5. 批量改名
6. 迁移导入

来源：

1. 桌面 `voice_settings.py`
2. Web `ProVoiceManager.vue`
3. Web `VoiceManager.vue`

### 3. `Assets`

职责：

1. 参考音频资产表
2. 上传
3. 删除
4. 试听
5. 绑定 / 解绑 voice
6. 编辑备注与 transcript

## 6. 技术方向

## 6.1 只保留一套 API 客户端分层

当前 Web 端存在：

1. `cosyvoice.ts`
2. `pro_client.ts`

后续方向应该是：

1. 保留一个统一请求底座。
2. 在底座之上拆分为：
   - `voiceApi`
   - `assetApi`
   - `synthesisApi`
   - `batchApi`
   - `systemApi`
3. 所有页面共用同一套鉴权、错误处理、URL 解析、Blob 播放逻辑。

目标：

1. 不再出现“有的能力在 `CosyVoiceClient`，有的能力在 `ProApiClient`”的分裂状态。
2. 不再让 UI 层自己处理过多协议差异。

## 6.2 只保留一套状态模型

当前 Web 端存在两类 store：

1. `pro_system / pro_voice / pro_task`
2. `project / voices / tts / libraries ...`

方向建议：

1. 以领域为中心，而不是以“pro/非 pro”分裂。
2. 目标状态域建议统一成：
   - `app`
   - `workspace`
   - `voices`
   - `assets`
   - `library`
   - `system`
   - `export`

原则：

1. 一条业务数据只应有一个权威 store。
2. 页面只消费领域 store，不再自己维护第二份简化状态。

## 6.3 组件层级重建

当前组件层已经混合了三种风格：

1. 通用面板型
2. Pro 工作站型
3. 临时功能型

后续应重建三层：

1. `App Shell`
   - 页面骨架
   - 顶栏 / 侧栏 / 面包屑 / 全局提示
2. `Feature Components`
   - VoiceTable
   - AssetTable
   - TaskTable
   - ScriptBlockEditor
   - SystemStatusBar
3. `Primitives`
   - Button
   - Input
   - Select
   - Dialog
   - Badge
   - EmptyState
   - StatusRow

## 6.4 UI/UX 规范

基于 `ui-ux-pro-max`，后续 Web 端应强制遵守以下规则：

1. 不再使用 emoji 作为正式信息层级或按钮语义。
2. 所有异步按钮必须有 loading + disabled 态。
3. 图标按钮必须有 tooltip / aria-label。
4. 焦点态可见，键盘路径完整。
5. 正文对比度符合可读要求。
6. 页面不再混合三种视觉系统，统一为单一设计语言。

建议视觉方向：

1. 产品类型：专业工作站 / 创作控制台
2. 风格：高信息密度、轻玻璃感、弱装饰、强状态反馈
3. 颜色：深底控制台 + 单一强调色，不再多套风格混搭
4. 图标：统一 Heroicons 或一套 SVG 图标系统

## 7. 哪些桌面能力应该迁，哪些应该重构，哪些应该放弃

## 7.1 必须迁入 WebUI 的能力

### A. 业务闭环级

1. voice 配置 CRUD
2. ref assets 管理闭环
3. 情绪变体管理
4. 任务计划与批量合成
5. 模型状态与系统控制
6. 工程导出/导入

### B. 质量保障级

1. 错误提示
2. 加载反馈
3. 操作日志或可追踪状态
4. 删除确认与撤销机制
5. 权限/鉴权正确处理

## 7.2 应重构而不是照搬的能力

1. 桌面文本染色编辑器
   - 建议重构为“结构化脚本块 + 行级角色/情绪/标签”
2. 桌面右键菜单能力
   - 建议改成工具栏 + 命令面板 + 快捷键
3. 桌面 refs inspector
   - 建议改为 Web 双栏或抽屉式资产面板
4. 桌面运维页
   - 建议缩减为 System 页面，只保留必要状态和模型操作

## 7.3 可以明确放弃 1:1 的能力

1. `QTextEdit` 级别的桌面富文本局部染色语义
2. “打开输出文件夹”这类依赖本机桌面壳层的行为
3. 内嵌 server thread 式的桌面生命周期管理
4. 纯桌面交互习惯形成的大量上下文菜单操作

说明：

放弃这些能力，不代表放弃对应业务；  
而是改成更适合 Web 的工作流。

## 8. 开发阶段建议

## M0：立即做出的项目级决定

目标：

1. 确认 WebUI 为唯一主线。
2. 确认桌面 GUI 停止新增功能。
3. 确认 `ProWorkspace` 为吸收整合的最终骨架。

执行要求：

1. 以后新功能优先进入 WebUI。
2. 桌面 GUI 仅允许：
   - 严重 bug 修复
   - 兼容性修复
   - 回归修复

交付物：

1. 本文档
2. 一份后续排期清单

## M1：收敛 Web 架构

目标：

1. 明确唯一入口和唯一页面结构。
2. 清理“Pro”和“通用工作台”的重复边界。
3. 设计统一的 API/store 分层。

完成标准：

1. 明确哪些通用 tab 会保留。
2. 明确哪些功能迁入 `ProWorkspace`。
3. 明确哪些旧页面会冻结。

## M2：优先完成 Voices + Assets 闭环

这是第一优先级，不应先做视觉打磨。

目标：

1. Pro 路线接入真实 voice CRUD。
2. 接入资产列表、上传、删除、试听、绑定、解绑、备注。
3. 做出情绪管理与 assets 的真实闭环。
4. 清理逻辑与后端接口对齐。

完成标准：

1. 用户无需桌面 GUI，也能完成 voice 与参考音频管理。
2. 桌面 `voice_settings.py` 的核心使用场景可在 Web 上跑通。

## M3：完成 Workspace 生产闭环

目标：

1. 剧本编辑
2. 导入任务
3. 单行运行
4. 批量运行
5. 行级参数控制
6. 合成结果试听
7. 批量结果回收

补齐项：

1. `mode`
2. `instruct_text`
3. `seed`
4. merge
5. 受鉴权音频播放
6. 任务计划保存/加载

完成标准：

1. 桌面 `text_edit.py` + `task_plan.py` 的主流程可以被 Web 取代。

## M4：完成 System + Settings + Export

目标：

1. 系统状态页
2. 模型控制页
3. 连接配置页
4. 导出/导入页
5. 可选的桥接说明或部署说明

这里要做一个取舍：

### 方案 A：桥接与 API 生命周期不迁

前提：

1. 后端由外部脚本、服务或容器启动。
2. WebUI 只负责连接与控制模型级接口。

优点：

1. 产品边界更清晰。
2. 更接近标准前后端架构。

### 方案 B：桥接与 API 生命周期继续迁入 Web

前提：

1. 产品目标仍然是“本地一体化工作站”。

缺点：

1. 复杂度更高。
2. 浏览器端不适合承担太多本地进程管理语义。

建议：

优先采用方案 A。  
即：WebUI 负责业务和系统状态，不负责完整本地进程编排。

## M5：桌面 GUI 退场

退场条件：

1. Voices + Assets 闭环已完成
2. Workspace 生产闭环已完成
3. System/Settings/Export 已完成
4. 有基础 E2E 回归用例
5. 有用户迁移说明文档

退场步骤：

1. 将桌面 GUI 标记为 legacy。
2. 启动脚本默认改为 WebUI。
3. README 和使用说明转向 WebUI。
4. 桌面端保留一段观察期，只修重大 bug。
5. 观察期结束后停止主线维护。

## 9. 具体模块方向

## 9.1 Workspace 模块

方向：

1. 用结构化脚本编辑取代桌面富文本染色。
2. 把“脚本编辑”和“任务计划”合成一个连续工作流。
3. 行级参数和批量参数分层展示，不做桌面表格的硬搬运。

建议交互：

1. 左侧脚本块
2. 右侧任务/结果面板
3. 顶部批量操作栏
4. 底部或右侧播放器与错误摘要

## 9.2 Voices 模块

方向：

1. voice 作为主对象
2. emotion 作为 voice 变体
3. assets 作为可复用资源

不要继续用“本地临时新增一条 voice 再说”的流程，必须统一真实数据源。

## 9.3 Assets 模块

方向：

1. 从“附属面板”升级为正式领域页面。
2. 支持表格视图和按角色/情绪过滤。
3. 支持 linked / unused / transcript completeness 等筛选。

## 9.4 System 模块

方向：

1. 只做必要系统控制
2. 不做过度桌面化的运维台

建议保留：

1. health
2. model loaded
3. GPU/VRAM
4. unload/reload
5. cleanup
6. baseUrl/apiKey 配置

## 9.5 Settings 模块

方向：

1. 不再照搬桌面所有路径设置。
2. 只有在“本地一体化模式”需要时，才保留本地路径项。
3. 默认产品化路径应以“连接后端服务”为准，而不是“控制本地文件系统”为准。

---

## 10. 桌面 GUI 冻结策略

建议立刻执行：

1. `ui/` 目录不再接收新功能需求。
2. 仅允许：
   - 崩溃修复
   - 数据一致性修复
   - 安全性修复
   - Web 迁移过程中的兼容修复
3. 任何新需求先判断能否直接进入 WebUI。

这样做的目的不是立即删除桌面，而是避免：

1. 迁移期间还在给桌面加新能力
2. 造成 Web 端永远追不上

---

## 11. 风险与应对

## 风险 1：继续出现两套 Web 主线

应对：

1. 明确只有一个正式工作流入口。
2. 重复功能只能保留一个。

## 风险 2：把桌面能力硬搬到 Web，导致体验更差

应对：

1. 坚持“保留业务、重做交互”的原则。
2. 不把 PyQt 交互细节当成产品需求。

## 风险 3：过早停止桌面维护，导致用户断层

应对：

1. 先做功能闭环，再退场桌面。
2. 设观察期与迁移文档。

## 风险 4：过多本地运维逻辑强塞到浏览器

应对：

1. 把本地进程编排从 Web 产品边界中剥离。
2. 优先做连接型 System 页面，而不是进程控制台。

---

## 12. 建议的近期落地顺序

如果只看未来 2 到 4 周的开发方向，建议优先级如下：

1. 明确 `ProWorkspace` 为唯一整合骨架。
2. 把通用 `VoicesStore` / `CosyVoiceClient` 的真实能力并入正式主线。
3. 先完成 `Voices + Assets`，再做 `Workspace` 细节补齐。
4. 在 `Voices + Assets + Workspace` 三块闭环完成前，不投入大量时间做视觉打磨。
5. 等核心闭环完成后，再统一信息架构、设计系统和导航。

---

## 13. 最终判断

本项目后续最正确的方向，不是“继续维护桌面 GUI，同时慢慢补 WebUI”，而是：

> 立即把 WebUI 定义为唯一未来产品；  
> 围绕桌面 GUI 的核心业务能力做 Web 原生重构；  
> 让桌面 GUI 进入冻结和退场流程。

这样才能做到三件事：

1. 研发主线单一
2. 功能收口可衡量
3. 最终可以真正放弃桌面 GUI，而不是长期双轨维护
